## Why there is no live observation

The app and the API were both running for real. The walk stops at the sign-in wall.

**What was actually run**

- `rs-backend`: `func start --port 7071` (Azure Functions Core Tools, `~/.local/opt/func`), using the
  repo's own `local.settings.json`, which has `AzureWebJobs.orderTimers.Disabled`,
  `AzureWebJobs.reconcileCheckouts.Disabled` and `AzureWebJobs.subscriptionTimers.Disabled` set to
  `true`. `nc -z localhost 7071` → open.
- `rs-superadmin`: `npm run dev -- --port 5174 --strictPort` from this worktree.
  `curl http://localhost:5174/login` → HTTP 200. `nc -z localhost 5174` → open.
  (`node_modules` and `.env.local` are symlinks to the main checkout — both are git-ignored and are
  not part of the diff.)
- Unauthenticated probes against the running dev API (read-only, nothing written):

  | request | response |
  |---|---|
  | `GET /api/shops` | `403 {"error":"Superadmin access required"}` |
  | `GET /api/users/me` | `403 {"error":"Authentication required"}` |
  | `GET /api/plans` | `403 {"error":"Authentication required"}` |
  | `GET /api/shops/usage?shopId=x` | `403 {"error":"Authentication required"}` |

  The API is reachable and its platform gate is closed to an anonymous caller, as designed.

**Where the walk stops**

Opening `http://localhost:5174/login` renders the "Superadmin Portal" card (evidence: attached
screenshot `c4-01-login-page.png`). Clicking **Sign in as Superadmin** navigates the browser to

```
https://login.microsoftonline.com/<WORKFORCE_TENANT_ID>/oauth2/v2.0/authorize
  ?client_id=<superadmin SPA app id>&scope=openid profile offline_access
  &redirect_uri=http%3A%2F%2Flocalhost%3A5174 …
```

which is the Microsoft **workforce** tenant (the tenant id is the one in
`rs-backend/local.settings.json` as `WORKFORCE_TENANT_ID`, and the authority comes from
`VITE_MSAL_AUTHORITY`), and lands on the Microsoft "Sign in" form (evidence: attached screenshot
`c4-02-msal-signin-wall.png`).

That form needs a real platform-operator account and any MFA/conditional access on it. The repo
holds no credentials, and `rs-e2e/playwright/.auth/` contains only `.gitkeep` — no captured
session. `rs-e2e`'s own capture script says so in its header comment: it is headed and interactive
on purpose, `npm run auth:superadmin`. `src/services/baseApi.ts` sends the MSAL access token from
`acquireTokenSilent`; there is no dev bypass, no mock-MSAAL mode, and no `VITE_*` flag that skips
auth (`grep` for bypass/mock/skip flags in `src` finds nothing).

So an agent cannot establish a session, and therefore cannot reach `/shops/:id/activity`,
`/shops/:id/usage`, `/shops/:id/subscription` or `/decline-watch`. All four are behind
`RequireAuth` (`src/auth/RequireAuth.tsx`). This is a **capability wall, not a code fault**.

**Nothing was written.** No shop's plan, limits, or override was changed; no scratch shop was
created either, so the "read-only against real data" boundary was met by not writing at all.

## 1 — Superadmin activity details (spec §21-8b TODO)

**Not reproducible live. A real defect was found and is fixed in this PR.**

Spec §21-8b records: *"Not yet seen: … the superadmin activity details (TODO)."* The activity log
(`src/pages/ShopActivityPage.tsx`) renders each audit row as
`<actor> <action sentence> <entity name>`, and expands to a before/after detail table when the
entry carries `changes`.

**Defect found (fixed): 15 audit actions the backend writes had no label, so the log printed the
raw key** — e.g. `shop.orders_auto_paused` appeared verbatim instead of a sentence. Method: every
`action: '<key>'` literal in `rs-backend/src` (47 distinct keys) was compared with the frontend map
(32 keys). The 15 missing ones: `shop.delete`, `shop.restore`,
`shop.missed_orders_pause_limit`, `shop.orders_auto_paused`, `shop.offline_by_superadmin`,
`shop.nameChange.requested|approved|rejected`, `staff.create|update|delete|password_reset`,
`reference_lists.update`, `role_permissions.update`, `platform_legal_identity.update`. Three audit
`entityType` values (`reference_lists`, `role_permissions`, `platform_legal_identity`) were also
unmapped and rendered as the bare type.

Fixed by moving the maps into `src/pages/shop-activity-labels.ts` and adding the missing entries,
worded against the handler that writes each one. Two of the obvious wordings were wrong and are
not used: `shop.missed_orders_pause_limit` is a superadmin *setting* the auto-pause threshold (it
does not pause anything), and `shop.offline_by_superadmin` is written both when a shop is taken
offline and when it is brought back. The new test file pins both facts.

**The delivery half of the §21-8b TODO is present in the backend.** `shop.order_settings_update`
is written with detail rows for `delivery`, `deliveryHours` and `deliveryZones`
(`rs-backend/src/application/shop/updateOrderSettings/executeUpdateOrderSettings.ts:190,209-222`),
so the data the "details" panel needs does exist. What was missing was the label.

**Unverified:** that a real delivery-settings change expands in the browser into readable
before/after rows. That needs a session plus a shop whose delivery settings are changed — a write
this packet is not allowed to make.

**Two further defects found; the fix belongs in `rs-backend`, outside this repo's boundary:**
- **B35** — override rows show the shop's UUID instead of its name. `entityName` is hard-coded as
  `` `Shop ${shopId}` `` in `executeSetLimitOverride.ts:73`, `executeClearLimitOverride.ts:39` and
  `executeCancelShopSubscription.ts:72`; those handlers never load the shop. Parked in
  `rs-backend/docs/deferred.md:271-280`.
- **A22** — a staff action's *target* shows the raw staff id: the staff use cases write
  `entityName: created.id` (`executeCreateStaff.ts:92`, `executeDeleteStaff.ts:59`,
  `executeUpdateStaff.ts:88`, `executeResetStaffPassword.ts:60`), and the audit reader resolves
  only actor labels. Parked in `rs-backend/docs/deferred.md:380-389`.

Both are read-time resolution problems in the backend audit reader. They were **not** papered over
from the frontend; they are handed off here instead.

## 2 — Usage page against the orders-per-month counter

**Not reproducible live. Code-level PASS — the counter cannot be reading products.**

- The API's usage DTO carries no product count at all. `ShopUsageDto`
  (`rs-backend/src/application/usage/shopUsageDto.ts:3-21`) is
  `{ shopId, periodKey, acceptedOrderCount, lastReconciled, updatedAt }`.
- The page reads exactly that field against the limit: `usage.acceptedOrderCount` over
  `data.ordersPerMonthLimit` (`src/pages/ShopUsagePage.tsx:19-45`), and renders
  "Accepted orders — {periodKey}".
- The number is maintained only when an order is accepted:
  `incrementAcceptedOrders(shop.id, usagePeriodKey)` in
  `rs-backend/src/application/order/_shared/acceptPlacedOrder.ts:240`, which bumps
  `acceptedOrderCount` (`src/application/_shared/usageCounter.ts:19-26`). Nothing else writes it.
- The limit shown is `PLAN_LIMIT_KEYS.ORDERS_PER_MONTH` from the shop's entitlements
  (`executeGetShopUsage.ts:53`), not a product count.

**Unverified:** that the number on a specific shop's screen equals that shop's accepted-order count
for the period. That is a measurement, and it needs a session.

## 3 — Plan / limit overrides with a reason and an expiry

**Not reproducible live. Code-level PASS.** No override was attempted, live or otherwise — this
boundary explicitly forbids changing a live shop's plan or limits as a test.

- Client validation: `planOverrideError` requires a plan and a non-empty reason; `limitOverrideError`
  requires an integer ≥ -1 and a non-empty reason (`src/pages/subscription-override.ts:13-28`), with
  its own unit tests.
- The request bodies match the backend DTOs field for field:
  `{ planId, overrideReason, overrideExpiresAt }` vs `OverrideShopSubscriptionRequestDto`, and
  `{ limits, reason, expiresAt }` vs `SetLimitOverrideRequestDto`
  (`src/pages/ShopSubscriptionPage.tsx:68-75,93-96`). A date-only input is converted to
  end-of-that-local-day in ISO (`endOfDayIso`).
- The backend re-validates and then persists both fields: reason must be 1–500 characters and
  `expiresAt` must be in the future, otherwise `INVALID_INPUT`; on success it stores
  `reason`, `expiresAt`, `setBy` and `setAt` on the subscription
  (`executeSetLimitOverride.ts:16-27,66`), and `overrideReason` / `overrideExpiresAt` for the plan
  override (`executeOverrideShopSubscription.ts:69-72`). Both write an audit entry.
- The generated client and the backend agree on these routes: all 87 paths match between
  `rs-superadmin/openapi/swagger.json` and `rs-backend/src/swagger/swagger.json`, and
  `/shops/{shopId}/subscription`, `/shops/{shopId}/subscription/override` and
  `/shops/{shopId}/subscription/limit-override` are byte-identical. (The two files are *not*
  wholly identical — the backend has since added an unrelated `CaptureConfigFailure` schema on the
  Order model and a changed TypeScript-generated schema-name hash. Nothing on these four surfaces
  differs. This corrects a claim in the previous attempt that the two files match.)

**Unverified:** that the PUT returns 200 and that the reason and expiry round-trip to the screen.
A GET returning 200 would not prove that anyway.

## 4 — Decline watch

**Not reproducible live. Code-level PASS.**

- The page (`src/pages/RejectionWatchPage.tsx`) reads `data.shops[]`, and per row
  `orderLimit.acceptedOrderCount` / `orderLimit.limit` / `orderLimit.warningLevel`,
  `rejections.rate`, `rejections.rejectedByRestaurant` and `rejections.flags`.
- The backend DTO matches: `RejectionWatchDto.shops[]` of
  `{ shopId, name, slug, orderLimit, rejections }` (`rs-backend/src/application/usage/rejectionWatch/dtos.ts`),
  where `orderLimit` is the same `OrderLimitStatus` the usage page uses, so the same accepted-order
  counter backs it. Rows are ordered flagged-first, then by rate.
- The route exists and is spec'd (`/usage/rejection-watch`, present and identical in both swagger
  files).

**Unverified:** the rendered table against real rows, and that the "flagged first" ordering is
visible.

## Incidental finding (not changed)

The generated `src/services/api.ts` uses 18 tag types that are not declared in the hand-written
`src/services/baseApi.ts` `tagTypes`: `Audit`, `Catalog`, `Categories`, `Combos`, `Data Privacy`,
`Legal`, `Platform`, `Product Images`, `Products`, `Promotions`, `Reference Lists`, `Reports`,
`Shop Cover Image`, `Shop Logo`, `Staff`, `Stripe`, `Users`, `Webhooks`. Five declared ones
(`AuditEntries`, `PlatformLegal`, `ReferenceLists`, `RolePermissions`, `UserProfile`) are never
used, which is the fingerprint of a half-finished migration. RTK Query
treats an undeclared tag as a dev-only `console.error` and still matches it at runtime, so this is
console noise and a stale list, not a functional break. Left alone: `api.ts` is generated and this
is not one of the four surfaces.
